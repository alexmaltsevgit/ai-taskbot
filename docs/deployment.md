# Деплой через GitHub Actions

Этот workflow — подготовка безопасного канала доставки, **не подтверждение, что сервер уже настроен**. Он запускается вручную, только для ветки `main`, и по умолчанию заблокирован отсутствующим `DEPLOY_ENABLED=true`. Мерж PR не запускает деплой. При ручном запуске с выключенным флагом проверки и сборка могут выполниться, но SSH-подключение блокируется.

## Граница доступа на общем сервере

На сервере с другими сервисами нельзя передавать GitHub Actions существующий root-ключ, добавлять deploy-пользователя в группу `docker` rootful-демона или давать ему общий `sudo`. Такой доступ практически равен root-доступу ко всем сервисам.

Данный вариант требует **отдельного пользователя без sudo/группы docker и отдельного rootless Docker engine**. Скрипт проверяет rootless и запрещает SSH-пользователя root. Уже установленный обычный Docker **не означает**, что это условие выполнено. Если rootless отсутствует, деплой блокируется. Установка отдельного пользователя/демона, lingering, SSH-ключей и необходимые изменения системных настроек сначала согласуются с владельцем; основной deploy-workflow ничего из этого не устанавливает. Отдельный ручной **Setup isolated rootless Docker** после согласования может настроить только пользовательский rootless-сервис через уже установленный официальный инструмент, как описано ниже.

Контейнеры работают с UID 0 **внутри rootless engine**, который отображается в UID выделенного пользователя хоста, а не в host root. Так они читают конфигурацию 0600 и записывают собственные данные 0700 без выдачи доступа другим пользователям. Файловая система контейнеров read-only, все capabilities отключены, включён no-new-privileges. Этот Compose-файл нельзя использовать с rootful Docker напрямую.

Изоляция развёртывания:
- фиксированный Compose project `ai-taskbot-production`, его отдельная сеть;
- данные только в `<DEPLOY_ROOT>/shared/data`, авторизация Codex в `<DEPLOY_ROOT>/shared/codex-auth`;
- runtime-конфигурация в `<DEPLOY_ROOT>/shared`, релизы в `<DEPLOY_ROOT>/releases/<commit SHA>`;
- только эти два сервиса останавливаются/обновляются; нет глобального prune, изменения Docker daemon, `down -v` или удаления чужих контейнеров;
- контейнеры не публикуют порты; внешний reverse proxy не нужен.

Если rootless неприемлем, нужен отдельный проект ограниченного rootful deploy-wrapper с проверенными разрешёнными операциями. Этот workflow не предоставляет такого обхода и не должен запускаться с rootful engine.

## Что нужно знать до первого запуска

1. Адрес SSH, порт, имя **выделенного** deploy-пользователя и доверенный публичный host key сервера.
2. Подтверждённая архитектура `linux/amd64` (другие архитектуры пока намеренно отклоняются), Bash, Docker Compose с `--pull never`, `flock`, `tar`, `gzip`, `sha256sum`.
3. Доступ SSH с GitHub-hosted runners. Не отключайте firewall и не открывайте сеть автоматически, если доступа нет.
4. Отдельный rootless engine, доступный **в неинтерактивной SSH-сессии**. В проверке должно быть `name=rootless`: `docker info --format '{{json .SecurityOptions}}'`. Нельзя подменять её доступом к rootful socket.
5. Каталог назначения, доступный только deploy-пользователю, достаточно места для двух образов, релизов и резервных копий.
6. Telegram-токен, чаты/пользователи/репозитории в `config.json`, GitHub App или PAT, WORKER_TOKEN и подходящая подписка ChatGPT.

Runtime-секреты размещаются владельцем непосредственно на сервере через доверенное подключение. **Не отправляйте приватные ключи, токены и файл Codex auth в чат или публичный репозиторий.**

## Настройки GitHub

Создайте Environment **production**, включите required reviewers и ограничьте deployment branch до `main`. При необходимости разрешите владельцу подтверждать собственные запуски. Если план/политика не поддерживает reviewers, не считайте environment автоматическим approval-gate: ручной запуск и `DEPLOY_ENABLED` всё равно обязательны, а порядок подтверждений согласуется отдельно.

Repository variable:
- `DEPLOY_PLATFORM=linux/amd64` — задайте только после проверки архитектуры. Она нужна build-job до входа в environment.

Environment `production` variables:
- `DEPLOY_ENABLED=true` — включить только после завершения согласованной настройки; отсутствие/любое другое значение блокирует подключение;
- `DEPLOY_PORT` — SSH-порт;
- `DEPLOY_ROOT` — абсолютный путь без пробелов/точек/спецсимволов, например `/home/taskbot/ai-taskbot`.

Environment `production` secrets:
- `DEPLOY_HOST` — IPv4 или DNS-имя (IPv6 пока не поддерживается); адрес не должен попадать в публичные логи как обычная variable.
- `DEPLOY_USER` — выделенный пользователь, не root; также secret для маскирования вывода диагностики.
- `DEPLOY_SSH_KEY` — приватная часть отдельного ключа для этого deploy-аккаунта, добавляется **напрямую в GitHub Secrets**, не через чат. Его публичная часть устанавливается на сервер только после согласования доступа. Не используйте общий root-ключ.
- `DEPLOY_KNOWN_HOSTS` — полная проверенная строка known_hosts для адреса и порта сервера. Для нестандартного порта имя имеет вид `[server.example]:22222 ssh-ed25519 ...`. Получите публичный host key через доверенную консоль/уже проверенное подключение и сравните fingerprint. Один только `ssh-keyscan` по непроверенной сети не является проверкой личности сервера.

Workflow использует `StrictHostKeyChecking=yes`, не принимает неизвестный/изменившийся ключ и не сохраняет секреты в artifact. Runtime-токены Telegram/GitHub и авторизация Codex в GitHub Actions не нужны. Ключи временно записываются только на одноразовом runner и удаляются после шага.

## Диагностика до установки rootless

Workflow **Diagnose deployment account** запускается вручную на `main` через то же окружение `production`, тот же `DEPLOY_ENABLED=true` и проверенные SSH secrets. Для него не нужны образы, `DEPLOY_ROOT`, `DEPLOY_PLATFORM`, runtime `.env`, Telegram/GitHub-токены или уже установленный rootless Docker.

Он передаёт проверенный скрипт по stdin SSH, не создавая файлов на сервере. Читает текущий UID/группы, ядро и архитектуру без hostname, наличие/права user runtime directory, наличие инструментов rootless/uidmap/slirp4netns и версии установленных клиентов/пакетов. `systemctl --user show` читает только LoadState/ActiveState/SubState; journal и содержимое конфигурации/секретов не выводятся. `loginctl show-user` читает только Linger/State.

Это не установка и не запуск сервисов: нет sudo, setup/install, изменения SSH/systemd/firewall, подключения к rootful Docker или доступа к соседним контейнерам. Неизвестный SSH host key по-прежнему блокирует подключение. Отсутствие runtime directory, user service manager или инструментов выводится как результат диагностики, а не исправляется автоматически. После результата отдельно согласуется необходимый bootstrap.

## Установка rootless после диагностики и согласования

Отдельный ручной workflow **Setup isolated rootless Docker** запускается только на `main`, через `production`, с теми же SSH secrets и `DEPLOY_ENABLED=true`. Он не требует runtime `.env` и не запускает приложение. Используйте его только после разрешения владельца на выделенный rootless-сервис.

Предварительные условия проверяются до вызова установщика: непривилегированный пользователь и принадлежащий ему home, каталог `/run/user/<UID>` с правильным владельцем и правами 0700, user systemd/D-Bus, включённый lingering, минимум 65536 subordinate UID и GID, наличие `newuidmap`, `newgidmap`, `slirp4netns`, `rootlesskit`, `iptables` и официального `/usr/bin/dockerd-rootless-setuptool.sh` из установленного пакета `docker-ce-rootless-extras`. Если чего-либо нет, workflow завершается без попытки установки сервиса.

На Ubuntu недостающие подтверждённые пакеты устанавливает администратор отдельно, после согласования:

```sh
apt-get update
apt-get install --no-upgrade --no-install-recommends -y uidmap slirp4netns
```

Не выполняйте общий upgrade и не меняйте работающий rootful Docker. Если не работают user D-Bus/systemd, сначала исследуйте причину; иногда нужен пакет `dbus-user-session`. Если отсутствуют iptables/доступные namespaces или lingering, не обходите проверки: согласуйте конкретное недостающее действие. Этот workflow не выполняет sudo, apt, modprobe, sysctl, изменение firewall или rootful-сервисов.

Скрипт вызывает официальный `check` и smoke test `rootlesskit true`, затем официальный `install`. **`--force` не используется**: в официальном инструменте он не только игнорирует доступный rootful socket, но и позволяет продолжить после неуспешного smoke test. Работающий rootful Docker других сервисов сам по себе не мешает установке, если его socket недоступен этому пользователю. Доступный rootful socket считается лишними полномочиями и блокирует workflow.

Установщик создаёт/запускает/включает только пользовательский `docker.service` и контекст `rootless`. Чужой существующий user unit или контекст с другим endpoint отклоняется. Уже корректно настроенный активный/включённый rootless-сервис повторно не устанавливается. Проверяется, что собственный socket отвечает с `name=rootless`. Если официальный установщик завершился частично, скрипт не удаляет автоматически сервис/данные: нужен осмотр, затем безопасный повтор.

Официальное поведение проверено по [исходнику Docker/Moby](https://github.com/moby/moby/blob/master/contrib/dockerd-rootless-setuptool.sh); [документация rootless Docker](https://docs.docker.com/engine/security/rootless/). Используется установленный пакет, ничего не скачивается и не исполняется из сети во время setup.

Для каждой SSH-сессии deployment-скрипт задаёт `DOCKER_HOST=unix:///run/user/<UID>/docker.sock` и снимает унаследованные `DOCKER_CONTEXT`/TLS overrides. Поэтому отсутствие настроек в shell profile не переключает деплой на rootful daemon. Для ручных команд используйте такую же явную привязку:

```sh
export XDG_RUNTIME_DIR="/run/user/$(id -u)"
export DOCKER_HOST="unix://$XDG_RUNTIME_DIR/docker.sock"
unset DOCKER_CONTEXT DOCKER_TLS_VERIFY DOCKER_CERT_PATH DOCKER_CONFIG
```

## Подготовка каталога после согласования доступа

Далее команды выполняются в сессии выделенного deploy-пользователя, **не root**. Подставьте согласованный каталог:

```sh
export DEPLOY_ROOT=/home/taskbot/ai-taskbot
umask 077
mkdir -p "$DEPLOY_ROOT/shared/secrets" "$DEPLOY_ROOT/releases"
```

Разместите там:
- `shared/.env` с `TELEGRAM_BOT_TOKEN`, `WORKER_TOKEN` (случайный, минимум 32 символа), `GITHUB_TOKEN` либо `GITHUB_APP_ID` + `GITHUB_INSTALLATION_ID`; необязательный `CODEX_MODEL`;
- `shared/config.json` с реальными числовыми ID и списками доступа;
- `shared/secrets/github-app.pem`, если используется GitHub App.

Эти файлы принадлежат deploy-пользователю, права `.env`, `config.json`, приватного ключа — 0600, каталогов — 0700. Не применяйте к этому rootless варианту инструкцию `chgrp 10001` из обычного Compose setup: отображение UID здесь другое. Скрипт создаёт собственные bind-каталоги `shared/data` и `shared/codex-auth` с правами 0700. Они не наследуют UID 10001 из образа.

Не переносите состояние уже работающего бота в эту схему вслепую. Остановите его в согласованное время, сохраните и сверяйте незавершённые операции, отдельно перенесите состояние/авторизацию. Другие сервисы трогать не нужно. Первый управляемый запуск отказывается автоматически принимать уже существующие контейнеры проекта `ai-taskbot-production` без файла текущего релиза.

## Первичная загрузка и вход Codex

1. В GitHub Actions откройте **Deploy AI Taskbot → Run workflow**.
2. Выберите `main` и режим **prepare**. Подтвердите environment.
3. Workflow проверит Go-код и deployment-скрипты, соберёт два amd64-образа, передаст их с проверкой SHA256 и загрузит в отдельный rootless engine. Публичный registry/GHCR не требуется. Расширенная runtime-конфигурация не печатается в логах.
4. На сервере укажите SHA **этого запуска** и выполните вход:

```sh
export DEPLOY_ROOT=/home/taskbot/ai-taskbot
export RELEASE_SHA=<полный-40-символьный-SHA-из-запуска>
docker compose --project-name ai-taskbot-production \
  --env-file "$DEPLOY_ROOT/shared/.env" \
  -f "$DEPLOY_ROOT/releases/$RELEASE_SHA/compose.yaml" \
  run --rm --no-deps worker codex login --device-auth
```

Откройте официальный адрес и код в своём браузере. При необходимости включите вход по коду устройства в настройках ChatGPT. Файл авторизации остаётся в `shared/codex-auth`, не в GitHub. `prepare` не запускает бота. Проверка `check-config` читает конфигурацию без polling и записи в GitHub.

5. Запустите workflow снова на `main` в режиме **deploy**. Если main изменился, будет подготовлен новый проверенный SHA; авторизация и данные сохранятся.

## Обновления, проверки и откат

Каждый деплой пересобирает проверенный main, не разворачивает произвольный пользовательский ref и не запускается из pull_request. Развёртывания сериализованы в Actions и локальным flock. Релизные образы имеют теги commit SHA.

Перед обновлением проверяются Compose-конфигурация, формат конфигурации приложения и наличие авторизации Codex. Затем останавливается только текущий poller бота и делается архив его данных. Архивы остаются в `backups/` с закрытыми правами. Автоматической очистки архивов/образов нет: администратор следит за местом и политикой хранения.

После запуска в течение 30 секунд проверяется, что оба процесса работают без рестартов. Это **не** проверка доступности модели, квоты подписки или полного Telegram → GitHub сценария. После первого запуска вручную создайте тестовую задачу через Telegram, проверьте preview, подтверждение и ссылку; затем проверьте дубль и `/edit` на тестовой задаче.

Если запуск или проверка процессов неуспешны, скрипт возвращает предыдущие образы/Compose-файл. При первой установке он останавливает только свои два сервиса. Данные и авторизация не удаляются и архив поверх текущего состояния автоматически не восстанавливается: такой откат мог бы забыть уже выполненные GitHub-операции. При ошибках после начала обновления, включая сбой резервной копии, проверки процессов или записи метаданных, EXIT-обработчик делает одну попытку отката. HUP/INT/TERM также приводят к этой попытке. Исходный код ошибки сохраняется. При ошибке самого отката требуется администратор; workflow не объявляет успех. SIGKILL, отключение хоста или отказ Docker не позволяют гарантировать выполнение отката.

Перед несовместимой миграцией формата состояния требуется отдельный план, автоматический откат образов не решает совместимость данных. Сейчас формат состояния остаётся прежним.

## Проверки разработки

`bash deploy/test-deploy.sh` проверяет аргументы, синтаксис и сценарии staging/deploy/rootful rejection/rollback через mock Docker CLI без доступа к настоящему Docker socket. Отдельный `bash deploy/test-rootless.sh` проверяет отсутствие установки при недостающих prerequisites, отказ от чужого context/service, изоляцию endpoint, повторный запуск и точный stdin-транспорт `bash -s` через mocks. Go race-тесты и vet выполняются отдельно. Реальное SSH-подключение, rootless engine и live-сценарий проверяются только после настройки и предоставления разрешённого доступа.
